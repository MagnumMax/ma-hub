# Сегментный review в `/MA-deploy` (Phase 0W + 1S + 1A)

**Цель:** на любом diff дать каждому куску полноценное внимание — не одним «средним» проходом по всему релизу.

**Только из `/MA-deploy`.** Не открывать ветки и GitHub PR на сегмент. Закон релиза тот же: одно дерево → атомарные commits **только выбранной волны** (3.9) → один push `dev` → один PR в `main`. Хвост следующих волн остаётся в дереве.

Логика нарезки — как у skill `split-to-prs` (смысл / владельцы / фундамент раньше потребителей). **Исполнение split-to-prs (ветки, push, PR) — запрещено.**

## Когда

**Всегда** (даже маленький diff → обычно **1 сегмент**). Не дробить искусственно: 1–2 связанных файла = один кусок.

## Diff scope

Uncommitted + при необходимости `main..HEAD` (кандидат в релиз). Не ждать Phase 3.9.

**Волна ≠ сегмент.** Волна — что уезжает в **этом** `/MA-deploy` (один push `dev` → один PR). Сегменты — куски ревью **внутри** волны. Потолка «~8 сегментов» **нет**.

## 0W — Волны (до нарезки кусков)

1. Разложить весь diff scope по **зонам продукта** (вход, кабинет, отчёты, хвост прошлой работы…). Считать строки: сумма added+deleted по файлам зоны (`git diff --numstat` + оценка untracked).
2. **Две и больше независимых темы** → это **несколько выкатов**, не один проход с кучей сегментов.
   - Показать таблицу волн (зона / ~строк / что внутри простыми словами / рекомендуемый порядок: фундамент раньше).
   - **Стоп** — ждать, какую волну выкатывать **сейчас**. Даже `auto`: это бизнес-решение, не «заодно всё».
   - Не выбранная волна: **не** ревьюить в 1A, **не** коммитить в 3.9, файлы остаются в дереве до следующего `/MA-deploy`.
3. Одна связная тема (даже большая) → одна волна, дальше 1S. Маленький diff → одна волна, обычно 1 сегмент.

Не сжимать смесь зон «чтобы уложиться в восемь кусков». Не дробить одну связную фичу на два выката только из‑за объёма.

## 1S — План сегментов (только выбранная волна)

1. Scope = файлы **этой** волны, не весь грязный ком.
2. Нарезать **логические** сегменты:
   - независимые зоны / владельцы — отдельно;
   - тесно связанные изменения — вместе;
   - фундамент (схема, auth, shared) **раньше** потребителей;
   - **мягкий ориентир размера: ~400–800 строк** (added+deleted) на кусок. Не жёсткий запрет.
   - меньше ~200 связанных строк → слить с соседним, если та же тема;
   - больше ~800 → резать, **если** внутри есть независимые подтемы; если кусок тесно связан — оставить целым и пометить «больше ориентира, связанный»;
   - 1–2 связанных файла не дробить, даже если мало строк.
3. Число сегментов — сколько нужно для нормального ревью. Минимум: 1. Мелочь сливать. **Не** склеивать разнородное, чтобы «было меньше восьми».
4. По каждому сегменту сразу проставить колонку «Ревью сверх `/code-review`» по правилу A1 (без спроса). Показать короткую таблицу и **сразу идти** (без «ок?» на план кусков) — пауза только на выбор волны (0W) и бизнес-решения позже.

| # | Сегмент | Файлы / зона | ~строк | Область (для путей) | Ревью сверх `/code-review` | Зачем такой порядок |
|---|---------|--------------|--------|---------------------|----------------------------|---------------------|
| 1 | … | … | ~520 | auth / home / … | — / bugbot / security / оба | … |

## 1A — Цикл на каждый сегмент (по порядку)

Жёсткий порядок внутри сегмента: **`/code-review` (+ bugbot/security по типу куска) → Critical/High fix → ponytail + автофикс → backlog**.  
К следующему сегменту — только после закрытия Critical/High, применения ponytail-фиксов (в дереве, **без** commit) **и строки доказательства**.

### A1. Ревью по типу куска (зона сегмента)

Приоритет находок: баги → регрессии → безопасность → пробелы в тестах.  
Гонять **только этот сегмент** (файлы/зона из таблицы 1S), не весь релиз скопом. Не спрашивать «какое ревью запустить».

| Что | Когда |
|-----|--------|
| **`/code-review`** | **Всегда.** Костяк куска. Взгляд ревьюера; в A2 критичное всё равно чинить (закон выката сильнее «не правь код» у самой команды). |
| **`review-bugbot`** | Кусок меняет **поведение**: логика, поток экрана, API, данные, состояние. Не гонять на правку только текстов / копирайта / формулировок. |
| **`review-security`** | Кусок про **вход, роли, платежи, персональные данные, секреты**. Чувствительный кусок → обязательно, даже если уже был `/code-review`. |

Оба специалиста на одном куске — нормально (поведение + доступ). Все три на правку текста — запрещено.

**Запрещено:**
- вызывать `/review` (меню «Bugbot или Security»: пауза на выбор и **только одно** из двух);
- подменять `/code-review` парой специалистов;
- гонять Bugbot/Security на весь diff релиза «заодно»;
- считать Bugbot/Security заменой ponytail (A3).

Нет файла skill на диске → блокер (Cursor-native: обновление Cursor / кэш skills). Findings всех проходов — по серьёзности, в чат. Critical/High из любого прохода → A2.

### A2. Сразу чинить Critical и High

- **Даже в safe** — для этой волны: Critical/High правятся в дереве без паузы «чини?».
- Не уезжать в другие сегменты «заодно».
- После фиксов — лёгкая проверка по затронутому (если дёшево).

### A3. Ponytail + автофикс (исключение для Phase 1A)

**Это отдельный проход, не часть code-review.** Ревью на ошибки / security / bugbot **не** заменяет.

1. Прочитать skill `ponytail-review` с диска (нет файла → блокер `install-external-skills.sh`). **Прочитать / поставить skill ≠ прогнать.**
2. Прогнать по **diff этого сегмента** (не всего релиза скопом). Формат findings — как в skill.
3. Показать findings **в чате** (не «в уме»): строки `L…: <tag> …` **или** буквально `Lean already. Ship.`
4. **Сразу применить** явные `delete` / `stdlib` / `native` / `yagni` / `shrink` в дереве (без commit).  
   Это **исключение** MA-deploy: skill сам по себе «только отчёт» — здесь агент **обязан** внести правки после отчёта.
5. Спорное / рискованное / «нужно бизнес-решение» — **не** резать молча → в backlog.
6. **Сразу записать строку доказательства** (таблица ниже). Без строки сегмент не закрыт — к следующему куску **нельзя**.

**Доказательство (копить строки на весь релиз):**

| # | Сегмент | net | Внесено явно | В backlog |
|---|---------|-----|--------------|-----------|
| 1 | … | `net: -12` или `Lean already. Ship.` | 2 (delete, shrink) / 0 | нет / 1 спорное |

Минимум на строку: `net: -<N>` **или** `Lean already. Ship.` Плюс сколько явных правок внесли (0 допустимо только при lean / `net: 0`).

**Не доказательство (тихий skip):**
- «прочитал / поставил skill»;
- «ревью чистое» / только code-review / security / bugbot;
- «нечего упрощать» без фразы `Lean already. Ship.` или `net: 0`;
- одна оценка на весь diff;
- пустая таблица 2b в отчёте `/MA-deploy`.

**Safe:** после автофикса, если оставшийся заявленный `net ≤ -80` (ещё есть неснятый жир, который не трогали как спорный) → стоп, ждать решения.  
**Auto:** пометить и продолжить (строка доказательства всё равно обязательна).

### A4. Backlog сегмента

В `SEGMENT_BACKLOG` добавить:
- Medium / Low из code-review;
- спорные ponytail findings без автофикса;
- кратко: файл / суть / рекомендация (чинить / отложить).

## После всех сегментов — сводный backlog

1. Склеить backlog, убрать дубли.
2. Показать таблицу решений (простым языком).

| # | Сегмент | Проблема | Серьёзность | Рекомендация |
|---|---------|----------|-------------|--------------|
| … | … | … | Med/Low / спорное | чинить / не чинить / отложить |

3. **Safe:** пауза — ждать по пунктам «чини» / «не чинить» / «отложить» (можно пакетом). Пока Critical/High всех сегментов закрыты **и таблица доказательства ponytail полная** — можно параллельно готовить 1B только если backlog пуст или пользователь сказал «остальное отложить, продолжай».  
4. **Auto:** дешёвые однозначные Medium — починить в дереве; остальное в отчёт и дальше 1B **только если** таблица доказательства полная.

**Gate до 1B:** число строк доказательства = числу сегментов 1S. Дыра → стоп, не typecheck/lint/tests, не 3.9, не push. Даже в auto — вернуться к A3 по дырявым кускам. **Не** наверстать одним ponytail на весь diff.

**Дыру нашли позже** (уже 1B / упаковка, ещё не push): не выкладывать. A3 по тем же кускам → явные правки → если код менялся, снова 1B → 3.8/3.9 заново, если уже упаковывали.

## Запреты

- Ветки / push / GitHub PR на сегмент.
- Полный test suite на каждый сегмент (suite — один раз в 1B).
- Commit до Phase 3.9.
- Коммитить в 3.9 файлы **вне** выбранной волны.
- Смесь независимых зон в одном выкате; сжимать её в «~8 сегментов».
- Жёстко резать связанный кусок по лимиту 800 / склеивать разнородное, чтобы попасть в 400–800.
- Тихий skip 1S/1A «diff маленький, ревью скопом» — при одном сегменте всё равно полный цикл A1–A4 на нём.
- Подменять сегментный проход одним параллельным Bugbot‖Security‖Ponytail на весь diff.
- Считать «прочитал skill» / «ревью без замечаний» доказательством ponytail.
- Идти в 1B / 3.9 / push без полной таблицы доказательства (строка на каждый сегмент 1S).

## Отчёт (минимум в таблицах `/MA-deploy`)

- Волна: какая зона сейчас / что отложено на следующие выкаты.
- Число сегментов + порядок + ~строк (без потолка «8»).
- По сегменту: Critical/High закрыты? **строка ponytail** (`net` или `Lean already. Ship.` + сколько явных правок)? сколько backlog.
- Сводный backlog и статус решений.
- Суммарный ponytail `net` по релизу.
- Пустая / неполная таблица ponytail = блокер, не «пропуск».
