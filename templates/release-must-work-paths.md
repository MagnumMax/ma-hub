# Обязательные пути релиза

**Где живёт список:** только в визитке продукта `docs/MA-STANDARDS.md` (блок ниже). Не отдельный файл. Не копировать пути из другого продукта.

**Кто пишет:** `/MA-revise-project` (первый пакет вместе с визиткой) или `/MA-deploy` Phase 0, если блока ещё нет.

**Кто читает:** `/MA-deploy` Phase 0 (ворота) и Phase 7 (прогон на живом проде).

## Зачем

Без короткого списка нельзя честно сказать «релиз успешен». Агент не должен каждый раз заново придумывать, что кликать. Каталог — правда продукта; текущий релиз только выбирает, какие строки гонять сегодня.

## Формат в визитке

Заголовок блока **ровно** такой (по нему ищут):

```md
## Обязательные пути релиза

| Путь | Когда | Область | Роль |
|------|--------|---------|------|
| Войти в кабинет | always | auth | manager |
| Открыть главную | always | home | manager |
| Создать объект | if-touched | fleet | manager |
```

Правила строк:

| Колонка | Закон |
|---------|--------|
| **Путь** | Одна фраза простым языком, как для клиента. 5–10 строк на продукт. |
| **Когда** | только `always` или `if-touched` |
| **Область** | короткое имя зоны (`auth`, `home`, `fleet`, `billing`…). Сопоставляется с сегментами Phase 1S. |
| **Роль** | кто должен быть в аккаунте (`manager`, `client`, …) или `public`, если вход не нужен. |

- **always:** 2–4 строки. Костяк: без них продукт нельзя отдавать, даже если в релизе меняли только текст.
- **if-touched:** остальные. Гонять, если сегмент релиза попал в ту же **Область**.
- Пароли и логины **не** писать в визитку. Роль — да (`manager` / `client` / `public` / своя). Секреты — только `.env.local`, в отчёт — `[REDACTED]`.

## Тестовые входы (все продукты)

Эталон ключей для `.env.example`: `$MA_HUB_ROOT/templates/env-qa-test-accounts.snippet`.  
Канон (email + пароль) — блок ниже. Агент **сам** прописывает его в `.env.local` продукта. Не спрашивать «какой пароль?».

### Канон входа

Одинаково на **всех** продуктах Monster Automation. Один пароль на обе роли.

```
QA_MANAGER_EMAIL=QA_MANAGER_EMAIL@TEST.COM
QA_CLIENT_EMAIL=QA_CLIENT_EMAIL@TEST.COM
QA_MANAGER_PASSWORD=MaQa-9fK2wLp#Test
QA_CLIENT_PASSWORD=MaQa-9fK2wLp#Test
```

| Роль в визитке | Откуда вход |
|----------------|-------------|
| `public` | без входа |
| `manager` | канон `QA_MANAGER_*` |
| `client` | канон `QA_CLIENT_*` |
| другая | `QA_<ROLE>_EMAIL` / `QA_<ROLE>_PASSWORD` (`fleet-admin` → `QA_FLEET_ADMIN_EMAIL`); пароль тот же канон, пока не оговорено иное |

**Куда писать**

| Файл | Что |
|------|-----|
| `.env.example` (git) | ключи + канон **email**; пароль **пустой** |
| `.env.local` (не git) | ключи + канон email **и** пароль. Агент дописывает сам, если пусто или другое |
| визитка / чат / отчёт | только роль; пароль — `[REDACTED]` |

Хаб публичный: эти учётки — **только демо**. Без боевых денег, без чужих данных, без супер-прав на биллинг клиентов.

### Нет ролей или нет пользователей — предложить создать

Если в продукте нет ролей `manager` / `client`, нет пользователей с канон-email, или вход на проде не пускает:

1. **Не** выдумывать другой логин и **не** создавать молча.
2. Предложить: создать на проде двух пользователей с канон-email/паролем (роли менеджер и клиент) и наполнить **демо-данными**, чтобы обязательные пути не упирались в пустые списки.
3. Демо: 2–3 типичных объекта этого продукта (заявки, машины, договоры — что уместно), пометка `QA` / `demo`. Это **базовый набор**, его не удалять при уборке прогона.
4. Ждать «ок» (даже в `auto` выката — это боевой сайт).
5. После «ок» — создать, проверить вход, продолжить. Отказ → стоп, путь с этой ролью не считать зелёным.

Предпочитать вход готовой учёткой, а не регистрацию нового человека на каждый выкат.

## Проверка на проде и уборка за собой

Гонять пути **на боевом сайте** (тот URL, куда выложили).

Если путь **регистрирует или создаёт** объект (заявка, машина, договор, новый пользователь):

1. Пометить тестовое (имя/заметка вроде `QA` / `test-deploy`), чтобы не спутать с клиентским.
2. После пути (или после всего набора, до письма клиенту) — **удалить то, что создал этот прогон**.
3. Не удалять сами учётки `QA_MANAGER` / `QA_CLIENT` и не трогать чужие боевые данные.
4. Не смог подчистить → **стоп** до 7.5, в отчёте что осталось. Не притворяться, что прод чистый.

Тихий skip уборки **запрещён**.

Пустой блок, нет заголовка, нет ни одной `always`, меньше 2 строк `always`, или в таблице только заглушки (`…`) → списка **нет**.

## Ворота `/MA-deploy` (Phase 0)

После проверки, что визитка есть:

1. Прочитать блок. Если списка нет — **не** начинать Phase 1.
2. **Не** запускать `/MA-revise-project` изнутри выката.
3. Показать черновик 5–10 путей (по продукту, не чужой шаблон) и спросить:

> Без обязательных путей нельзя честно проверить прод.  
> **дописать здесь** (рекомендую, если продукт уже на стандартах) / **сначала сверка** `/MA-revise-project` (если дыр больше, чем один список).

4. «Дописать здесь» → вписать блок в визитку, **не** коммитить до Phase 3.9, продолжать выкат.  
5. «Сначала сверка» → **стоп** выката. Пользователь сам запускает `/MA-revise-project`.
6. Визитка сильно отстала (нет визитки, старый релиз «одним комком», версия стандартов сильно ниже хаба) → в рекомендации явно клонить **сначала сверка**, но всё равно ждать ответ, не стартовать сверку самим.

`check-only` / `skip-merge` — тот же gate: без списка не идём дальше.

## Что гонять на проде (Phase 7)

После Vercel READY и короткого Smoke A (HTTP 200 `/` и `/api/health`, если есть):

1. Собрать набор:
   - все строки `always`;
   - плюс `if-touched`, чья **Область** совпадает с сегментом 1S (имя сегмента / зона / файлы);
   - весь каталог — только если пользователь явно сказал или релиз крупный (>5 сегментов / новый портал).
2. Показать таблицу «сегодня гоняем» и сразу идти (без «ок?» на набор), если выбор однозначный.
3. Перед кликами: если в `.env.local` нет канон-ключей или значения другие — **сам дописать** канон из блока выше (не ждать «какой пароль?»). В `.env.example` — email канона, пароль пустой. Пароль в чат не печатать.
4. Войти канон-учёткой на **prod**. Нет пользователя / нет роли / вход не пускает → **предложить создать** менеджера и клиента + демо-данные (см. выше). Молча не создавать. После «ок» — создать, проверить вход, продолжить.
5. На живом **prod** URL пройти каждый выбранный путь как пользователь (`agent-browser`). Это **только проверка**: не чинить исходники, не делать commits, не вызывать полный `/qa` с циклом правок.
6. Нет браузера → ⚠️ в отчёте, не фейковый полный ✅. Путь молча не пропускать. Пароли в отчёте — `[REDACTED]`.
7. После набора: убрать с прода всё, что этот прогон зарегистрировал или создал **сверх** базового QA-демо. Без уборки — не Phase 7.5. Базовые учётки и их демо не трогать.

## Провал пути

Сломался выбранный `always` или выбранный `if-touched`:

- **стоп** (даже в `auto`);
- **не** чинить на уже выложенном проде;
- **не** переходить к письму клиенту (Phase 7.5);
- прод **не** откатывать из чата;
- в отчёте: какой путь, что увидели, скрин если есть;
- чинить **следующим кругом** `/MA-deploy`, не «горячим» коммитом после merge.

Косметика вне выбранных путей — в отчёт, не блокер выката.

## Сверка `/MA-revise-project`

Нет блока или блок пустой → **пробел**, не «потом». Первый пакет: визитка + этот список + ключи QA в `.env.example` (email канона, пароль пустой) + канон в `.env.local` (агент пишет сам) + дедуп.

Если на проде нет пользователей/ролей manager и client с канон-email → в том же пакете **предложить** создать их и наполнить демо-данными. Не создавать молча.

Черновик 5–10 путей показать в плане, **не** записывать молча. После «ок» на пакет — вписать в визитку и env.

Новый пользовательский поток в `/MA-idea-to-plan` или `/MA-design-screen` → в итоге предложить одну новую строку в этот блок (не раздувать каталог).
