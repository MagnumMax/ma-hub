# 05 · Release and quality

**Версия стандартов:** см. `VERSION`

## Перед релизом (минимум)
- [ ] Сборка проходит
- [ ] В визитке есть блок обязательных путей релиза (эталон `templates/release-must-work-paths.md`)
- [ ] Критичные пользовательские пути проверены **на проде** по этому списку (костяк `always` + затронутые `if-touched`)
- [ ] Входы: канон хаба в `.env.local`; на проде есть менеджер и клиент (или «ок» на создание + демо); что создали за прогон сверх демо — убрано
- [ ] Нет секретов в диффе
- [ ] Env на проде актуальны
- [ ] Миграции (если есть) понятны и обратимы или с планом
- [ ] Preview / staging проверен, если доступен
- [ ] Проверка простоты (`ponytail-review`) в Phase 1A `/MA-deploy` **с автофиксом** и **доказательством**: **одна** строка `net` или `Lean already. Ship.` на выбранную волну; «прочитал skill» / обычное ревью ≠ шаг. Нет строки → стоп до проверок и merge. При оставшемся `net ≤ -80` в safe — решение до merge

## Релиз-ритуал
Использовать `/MA-deploy` — полный пайплайн (ревью волны, ponytail один раз, тесты, build, merge, prod, обязательные пути).
В Phase 0: нет блока путей в визитке → стоп; дописать в этом выкате или сначала `/MA-revise-project`. **Не** запускать сверку изнутри выката.
В Phase 1: сначала зоны продукта (эталон `templates/segmented-review-ma-deploy.md` §0W): смесь независимых тем → **несколько выкатов**, стоп пока не выбрана волна (даже в auto). На выбранной волне — **один** `/code-review`; `review-bugbot` если тема меняет поведение (не только тексты); `review-security` если вход/роли/платежи/PII/секреты; **не** вызывать `/review`; **не** нарезать на куски; **не** ревьюить чужие темы. Затем Critical/High сразу → **один** ponytail с автофиксом **и строкой доказательства** → backlog; без строки 2b **не** typecheck/tests и **не** merge. Ошибки в файлах другой волны **не** блокер: спрятать на время проверок, не чинить «заодно». 3.9 коммитит только выбранную волну, затем возвращает спрятанное. Специалисты не заменяют `/code-review` и не заменяют ponytail.
**Сначала** проверки и правки по рабочему дереву; **атомарные commits** — сам агент **в конце** локального цикла (перед push), без спроса. Фиксы в середине **не** коммитить по одному.

### Глубокая чистка ≠ релиз
`/MA-product-pass` — прогон модулей с **simplify** (эталон `templates/simplify-ma-product-pass.md`): **убери ИИ-стиль** (словарь + рельсы: шум сразу, контракты URL/БД/API — не молча); не commit/push/prod.  
Не подменять product-pass деплоем и не ставить ponytail вместо simplify в product-pass. После чистки выкат — только `/MA-deploy`.

Карта всех ритуалов и **три упрощения** (не смешивать): `templates/ma-command-map.md`.  
Идея/фича — вкус `ponytail`; полный прогон — simplify «убери ИИ-стиль»; выкат — ponytail с автофиксом один раз на волну.

### Скорость релиза (анти-повторы) — все проекты

Правила ниже — **обязательны** для любого продукта на `/MA-deploy`, не локальная договорённость одного репозитория.

- Полный test suite — **один раз** локально в Phase 1 (+ тонкий CI). **Не** на каждый атомарный commit.
- **Git-хуки** — жёсткий gate в Phase 0 `/MA-deploy` (зеркало thin CI): тяжёлый pre-commit = блокер; в auto чинить по `templates/git-hooks-ma-deploy.md` + `MA_ATOMIC_PACKING=1`; в safe — стоп до «чини».
- **Форма CI (минуты Actions)** — минуты = число runner-job’ов × число запусков на коммит. Эталон: `templates/ci-ma-deploy.md` (+ `ci-ma-deploy.yml`): один job (install → typecheck → test), только `push` на `main`/`dev`, `concurrency` с cancel-in-progress. Дубль `pull_request` в своём репо без форков = блокер; исключение — Local deviations «есть форки».
- Перед push/PR: влить `origin/main` в `dev` и снять конфликты (**Phase 3.95**). Не открывать PR «вслепую» и ловить конфликт вторым кругом CI.
- Перед локальным build: проверить свободное место; при нехватке — безопасная очистка `.next` (и аналогов), чтобы не ловить ENOSPC.
- В статусе процесса явно писать **что ждём** и **сколько обычно занимает** (CI ~3–10 мин, Vercel ~5–10 мин).
- Thin CI (`typecheck`+`test`) и локальный `pnpm build` перед push — **обязательны**, не ослаблять. Экономим **дубли job’ов/событий**, не покрытие.

## Правило пауз (все длинные /MA-*)

Спрашивать / останавливаться **только** когда нужно **бизнес-решение** пользователя (цель, среда, направление дизайна, «чинить или нет», удалять ли файлы, **дописать обязательные пути или сначала сверка**, **создать QA-учётки и демо на проде**, **уведомлять ли клиента в Telegram после релиза**, **добавить ключи Telegram**, **согласовать текст апдейта**).

**Не** пауза и **не** «авария»:
- промежуточная техническая упаковка (коммиты, сохранение ради процесса)
- ожидание CI / Vercel (писать ETA в статусе, не спрашивать «ок подождать?»)
- «сначала красиво зафиксируем, потом продолжим проверки»
- вопросы про дробление коммитов / «ок по истории»

**Сначала довести** проверяемый результат → **потом** один раз упаковать/записать, если это вообще нужно для следующего шага.
В отчётах **всегда** блок «Статус процесса» из `00-operating-model.md` (сейчас / что происходит / ждём / обычно занимает / что от вас) — отделяй «нужно ваше решение» от «идёт процесс».
Внешние skills подтягиваются из upstream по `registry/external-skills.*`, не из копий в хабе.

## После релиза
- На живом **проде**: костяк `always` + затронутые `if-touched`. Вход — канон хаба (агент сам пишет `.env.local`). Нет ролей — предложить создать + демо, не молча. Что создали за прогон сверх демо — **убрать до письма клиенту**. Провал пути или неубитый тестовый объект → стоп, письмо клиенту не слать.
- **Клиентское уведомление в Telegram** — Phase 7.5 `/MA-deploy`: только после зелёных обязательных путей. Вопрос **да / нет (только техника)** → если да: ключи → черновик **English** в стиле **Slack/GitHub Changelog** (What's New / Improvements / Fixes; простые буллеты **без** Zone→Sub-area; полное полезное покрытие — **не** ужимать до «топ-6»; скан PR/diff/экранов, не только subject коммитов; один тон для всех продуктов) → согласование → отправка. Эталон: `templates/telegram-customer-update-ma-deploy.md`. «Нет (только техника)» / «не слать» — ⚠️ в отчёте, прод не откатывать.
- Краткий отчёт: что вышло, какие пути проверили, риски, что мониторить, ушёл ли апдейт клиенту
- «Следующие задачи» — по правилу пользователя
